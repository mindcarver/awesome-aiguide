# 内容分析：llm-cache-read-write-agents.md

## 亮点与关键见解

- **核心论点**：LLM 缓存是「逐 token 完全相同的前缀」KV cache——读缓存（0.1 倍价）确定性命中，写缓存（1.25 倍价）是一次投机
- **最反直觉的事实**：改一个 token，整条缓存链作废。因为缓存块 hash 链是连坐的，第 N 块的 hash 包含第 N-1 块的 hash
- **最贵的错误**：往系统提示里塞时间戳/动态内容——系统提示在缓存链最前面，一变全废
- **Agent 的结构性优势**：每回合历史走读缓存（越来越大），新增内容走写缓存（很小不变），读写比越来越好
- **金句**：「读的命中由你控制，写的命中由未来控制」
- **金句**：「命中率和质量冲突时，选质量」
- **隐蔽的坑**：OpenAI 自动缓存默认把断点放在最新 user/tool 消息处，导致共享前缀吃不到缓存
- **上下文压缩的双重伤害**：不仅缓存链断裂，摘要还丢掉了 assistant 决策细节

## 对读者重要的信息

- 缓存块 hash 链的连锁失效机制——这是理解「改一个 token 全废」的关键
- 断点放置规则：放在「最后一段稳定内容」之后，不是第一段可变内容之前
- 写缓存回本条件：前缀重复 ≥2 次 + 长度达标 + 内容稳定，三条缺一不可
- TTL 5 分钟但命中自动续期的机制
- `cache_read_input_tokens`、`cache_creation_input_tokens`、`input_tokens` 三个监控指标
- 上下文压缩的正确用法是「救急，不是日常」
- 预热技巧：`max_tokens: 0` 请求先把前缀写进缓存
