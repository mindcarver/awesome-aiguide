# dsh 插件生态：四千个插件、五个市场和一场度量战争

> `dsh` 开源约一个月，插件生态冲到近四千个登记插件、一万三千多个打了标签的仓库、五个第三方市场，而官方没有开市场。更拧巴的是度量：星数榜的头部被挂标签的无关产品占据，一个 3.5 万星的项目被实证与 `dsh` 没有一行代码关系；按 npm 周下载排序的榜单才还原真实装机，第一名每周二十万次。本篇按 2026 年 9 月 5 日的快照拆三件事：度量为什么失真（答案在官方自己开的通道里）、谁在真实被安装、以及一套挑插件的实际判断。生态月增是数量级的，数字用过即弃，判断方法比数字耐用。

## 一个装插件的下午

从一个具体任务出发：你要给 `dsh` 装一个侧边栏工作台插件，希望在聊天旁边直接编辑文件、开终端、看 Git 状态。这个任务会贯穿全文，因为它是度量的唯一意义：帮你从几千个候选里挑出该装的那一个。

你打开聚合市场 dshget，按 star 排序，榜首是一个 4.2 万星的项目：reactive-resume，一个开源简历构建器。它和 `dsh` 的关系是零，唯一的连接是它的仓库挂了 `dsh-plugin` 这个 GitHub topic 标签。你的任务在星数榜上第一步就摔倒了。

这不是孤例。3.54 万星的 DeepSeek-Reasonix 也挂在榜单头部，实际查证过：它是一个独立的 Go 语言编码 agent，有自己的扩展协议、Go SDK 和 ACP 实现，README 通篇没有提到 `dsh`。顺带把"查证"的方法交代了，你以后用得上：clone 下来 grep 一遍 `@deepseek-ai` 和 `dsh` 的 import，看 package.json 的依赖表里有没有 Cordis 系的包，读 README 找不找得到挂载说明。三步走完，一个仓库和 `dsh` 有没有真实代码关系，答案就有了；星数榜从不做这三步，它只数星星。简历工具、图床工具、低代码平台都在榜单上，挂标签的成本是一次点击，收益是进入一个二十一万星仓库辐射出的流量池。

问题出在哪？要回答它，得先看这个生态的官方通道是怎么设计的。先交代本文说的"度量战争"是什么：一个生态需要有信号告诉新人"装什么"，官方没开市场，信号的生产就落到了社区手里；谁生产信号、用什么口径生产，决定了千万次安装决策的流向，围绕口径的竞争就是这场战争。它不体面，没有宣战书，但每天都在打：抓取源选哪个、排序键用什么、进榜要不要门槛，每一个选择都是一次站队。

## 失真是怎么造成的：从官方通道说起

`dsh` 官方没有插件市场。README 的 Community 一节写得很清楚：反馈走 GitHub Discussions，插件的可发现性靠给仓库挂 `dsh-plugin` topic，外加一个 Discord。也就是说，官方钦定的"插件登记处"是一个开放的 GitHub 标签：任何人、任何仓库、不需要审核、不需要一行代码关系，点一下就能挂上。

这个设计有其道理。开放标签的维护成本为零，不会变成官方的审核负担，也不会被指责准入歧视；对真插件作者来说，挂标签的摩擦也最小。但它有一个内生的代价：标签只证明"想要曝光"，不证明"是插件"。GitHub topic 从设计上就不校验内容，它是一个自我声明的分类。

然后第三方聚合市场来了。dshget 这类站点的做法是抓取 `dsh-plugin` topic 下的全部仓库，按星数排序呈现。两个机制叠在一起，星数作为"插件热度"的信号就废了：它度量的不再是"多少 `dsh` 用户装了它"，而是"多少 GitHub 用户给这个项目点过星，以及这个项目想不想蹭一个热仓库的流量"。星数和插件身份之间的因果关系，被开放标签从根上切断了。

把这条因果链排开看更清楚：

```text
官方登记通道 = 开放 topic（自我声明，不校验）
        +
聚合市场排序 = GitHub 星数（度量全站注意力，不度量安装）
        =
榜单头部 = 全站注意力最大 且 想蹭曝光的自我声明者
```

简历构建器恰好是全站注意力最大的那类项目（人人都需要简历），挂标签的动机又真实存在（二十一万星的辐射流量），两个条件一叠加，它必然出现在榜首。星数榜不是被个别坏 actor 污染的，是结构性地度量错了东西。

星数榜上也有真项目，后面会讲到 9.4 万星的设计引擎这种货真价实的插件。问题不是榜上全假，而是排序已经失真：你无法从头部的星数推断任何东西。回到下午的任务：侧边栏工作台到底装哪个，星数榜给不出答案。

## 生态的真实尺寸

先把盘子铺开，数字都以 2026 年 9 月 5 日为准，全部用过即弃。

官方仓库本身约 21 万星（话题页与讨论页两个来源交叉一致）。打了 `dsh-plugin` 标签的仓库 13,760 个，语言分布是 JavaScript 7,795、TypeScript 4,610、Python 543、Rust 106。写插件的主战场是 TS 和 JS，这与 `dsh` 的插件机制一致：插件是 Cordis 包，进 Node 进程，和宿主同生共死。Python 和 Rust 的绝对数量小，但它们的存在本身是个信号：那 543 个 Python 仓库里，有多少是写给 `dsh` 的工具型 MCP server，有多少只是来蹭标签的，没人统计过，这个盲区后面还会回来。

一个月 13,760 个挂标签仓库，这个速度要放在参照系里读。VS Code 的扩展生态花了数年才到六万级，Obsidian 插件三年到数千。`dsh` 一个月的登记量抵得上别人数年，原因不难找：写一个 Cordis 插件的门槛（一个包、一个 apply 函数、一次 npm publish）低于写一个 VS Code 扩展，叠加 AI 辅助编程把"写一个能跑的插件"的成本再压一个数量级。#1884 那篇 AI 生成插件风险综述出现的时机佐证了这一点：生态自己都已经在讨论"大量插件是模型写的"这件事了。速度是中性的，但它决定了这个生态的默认假设：数量不筛质量，质量要自己验。

市场有五家以上。dshget 收录 3,993 个插件、23 个分类，聚合四个来源；dshmarket 收录 3,019 个、24 个分类，每天 CI 刷新；另有 deepseek404、dsh.so、dsh-plugins.org 三家目录，数据普遍滞后（dsh-message-edit 在其中一家记 13 星，实测 49）；还有商业公司 SpringBrand 把自己的 OAuth MCP 插件市场整个装进 `dsh`。

五家市场不是重复建设，它们在口径上分成了两代。第一代是聚合目录：抓 topic、按星排、展示分类，dshget 是代表，胜在收录广，输在继承了星数的全部偏差。第二代开始经营信任：dshmarket 锁定自己的注册表（不照单全收聚合源）、默认禁用安装期 build script（防供应链攻击面）、不收遥测（装了什么不出你的机器）、按下载排序。市场竞争的维度从"收录多少"换成了"口径多干净"，这就是度量战争的正面战场：用户被骗一次之后，会用脚投票给口径诚实的那个。三代目录（deepseek404 等）数据滞后却还活着，说明还有一批用户只要"能找到名字"就够，分层的需求养得起分层的市场。第五种形态是 SpringBrand 那样的商业内置：不面向公众做目录，把自己的插件市场作为产品装进 `dsh` 分发给自己的客户，市场从"公共导航"退化成"私有货架"，这是 To B 侧对插件机制的另一种用法，和前四家不在同一条赛道。

注意一个有趣的递归：插件市场之上又长出了插件，"市场与管理器"在 dshget 自己就是一个分类，67 个条目，装一个插件来管理你从市场装的插件。递归不一定是坏事，它说明插件机制的表达能力足够强，连"管理插件"这件事本身都能被插件化；但它也提示生态的入口层已经多到需要再包一层，这对新用户是认知负担。

官方没有市场，那总账本在哪？事实上的总账本是 awesome-dsh-plugin，14.5k 星，收录 2,663 个插件，每日 CI 刷新，234 个 open PR 排队等合并。一个没有官方店的生态，账本由志愿者维护，合并速度跟不上提交速度，这本身决定了后面所有度量的混乱：没有一个权威的"什么是插件"的判定源，每个市场只能自己定口径。

官方为什么不开市场？从激励结构看是理性选择而不是没来得及。pre-1.0 阶段 API 每几天动一次，官方市场一旦开出，就等于给插件兼容性做了隐性背书，每次破坏性变更都会变成官方的信誉负债；把可发现性外包给开放标签、把策展外包给社区，官方只对 Discussions 秀场里自己转发过的东西负责。这个姿态的代价已经写在前面：登记处不设门槛，度量从根上就乱了。收益和代价是同一枚硬币，官方选了现阶段付得起的那一面。

## 下载榜：装机量的口径

dshmarket 做了一件关键的事：不按星数排，按 npm 周下载排。这个换法为什么成立？因为 `dsh` 插件的安装动作就是 npm install，一次下载对应一次安装（缓存和 CI 会带来重复计数，所以它度量的是"装机热度"而不是精确的用户数，这点瑕疵远小于星数的偏差）。下载量和"这是个真插件"之间的因果是紧的：没人会去下载一个和自己无关的简历工具。蹭标签能骗过抓取，骗不过装机。

榜单头部（周下载，2026 年 9 月初）：DSH-better-sidebar 207,883 次，侧边栏工作台，文件编辑、终端、Git 一个不少；dsh-task-board 205,086 次，看板加上 cron 定时调度 agent 会话；dsh-remote-web-ui 203,984 次，手机扫码远程控制；dsh-git-graph 200,623 次；dsh-skill-explorer 145,439 次。

两个观察。第一，下载榜头部的星数只有 3,267，与星数榜头部的四万级差一个数量级。星数和装机严重脱钩：真被装的东西不太涨星，涨星的东西不太被装。这个脱钩本身值得停一秒，它意味着两个榜单度量的根本是两种成功：星数度量的是项目在 GitHub 上的注意力（路过的人点了赞），下载度量的是它在工作流里的位置（装了且依赖）。你要挑的是后者。

第二，前十里有一半出自同一个作者（zhu1090093659），一人四件：task-board、remote-web-ui、git-graph、skill-explorer。插件作者生态不是长尾散沙，出现了多产作者。这是职业化的早期信号：一个人连续维护四个高装机插件，说明他在靠这套手艺吃饭，或至少认真投入，质量信号强于任何单品的星数。四件产品的品类选择也值得读：看板、远程、Git 可视化、技能浏览，全是工作台基础设施，互相不成竞争却共享同一批用户，一个作者在自己的用户群上做交叉销售。这个打法在成熟生态里叫产品矩阵，在月龄一个月的生态里出现，说明参与者已经开始做长期打算。

回到下午的任务：装哪个侧边栏工作台？答案在下载榜第一位，不在星数榜任何位置。DSH-better-sidebar 每周二十万次下载，功能清单正好覆盖你要的编辑、终端、Git 三件事。任务完成，但度量战争本身值得再挖两层：谁在真做项目，以及名气和体量为什么会倒挂。

下载榜的构成还有一层信息，它是一份没有伪装的产品遥测。头部五件：侧边栏工作台、任务看板加 cron 调度、手机远程控制、Git 图、技能浏览器。拼起来是一幅用户画像：人们在把 `dsh` 当长期工作台用，要文件要终端要版本控制，要离开桌面也能摸到，要把 agent 会话排进日程。没有一个头部插件是"更聪明的聊天"，全是"更顺的工作现场"。这个信号对插件作者比对用户更有用：生态的需求重心在工程化增强，不在提示词魔法。

## 真认真身的项目

以下是经查证确认存在的项目，按"它们说明生态的什么"分组。查证的标准只有一条：仓库里存在与 `dsh` 插件机制真实对接的代码或配置，而不只是挂了标签。

消息编辑双雄。`dsh` 官方曾实现会话消息编辑，随后 revert。这个 revert 的含义值得展开：官方没有说这个功能不该有，而是选择不在内核里固定一种编辑语义（会话日志是 append-only 的事件流，"编辑"在这个地基上有好几种投影方式：改写、撤回、分叉，每种都牵动"模型可见即可重建"不变量的实现细节），让插件生态去试不同的答案。承接的两个项目走了不同路线：DSH-EasyRewrite（96 星）做原位编辑加惰性撤回，被官方秀场帖子转发，是增长最快的插件之一；dsh-message-edit（49 星、19 fork）做分支式编辑，消息长成版本树，还暴露 HTTP API。同一个需求两条产品路线，生态多样性的标本，也是官方"让出去"策略的第一份回报。用户是赢家：不用等官方在两种语义里二选一，两装两试，用脚投票。

大厂把 `dsh` 当集成目标。火山引擎官方的 OpenViking（35.5k 星），自进化上下文数据库，仓库里带着真实的 `dsh-memory-plugin` 示例。这是目前最大厂的背书：不是给 `dsh` 贡献代码，而是把自己的产品做成 `dsh` 的下游。对生态而言，下游集成比上游贡献更值钱，它证明这个 harness 的接缝对外部产品是有用的。

出圈的非 coding 项目。open-design，9.4 万星，自称设计领域的开源替代，把编码 agent 变成设计引擎，导出 HTML、PDF、PPTX、MP4；archify，4.8 万星，生成架构图、时序图、数据流图。这两个项目也解释了星数榜为什么还有救：它们既是全站注意力大户，又是真插件，属于"挂不挂标签都会被找到"的那类。`dsh` 的分类学里非编程插件合计五百多个，这两个是天花板，也划出了 harness 通用性的一种证明：一个为写代码设计的执行底座，接上设计领域的工具后照样转。

桥接与发行层。dsh-desktop（23.6k 星）做桌面端，口号是"桌面本身也是插件"，这句口号的分量在于它把"包一层原生壳"也纳入了插件化的版图：桌面壳不 fork 源码，而是作为又一个 profile 加挂载层存在。dsh-acp 让 Zed 经 JSON-RPC 驱动 `dsh`，把官方的 acp profile 再往易用方向推了一步；deepseek-harness-sdk-go 补上官方没有的 Go SDK，说明控制面的语言缺口在被社区按需填。这一层填的全是官方没做或不急着做的缝，它们的存在检验了接缝设计的一个承诺：外围能力不需要上游排期，看得到缺口的人自己就能补。

fork 方向倒是安静：2.49 万个 fork 里，没有找到确认"fork 魔改成自己产品"的实例。两万多个 fork 几乎全是"克隆来读、克隆来跑"的动作，没有沉淀成维护中的分叉。这个安静和下一节的发行版现象互为印证：改造的欲望存在（否则不会有 overlay 发行版），但出口全都走插件层。

## oh-my-dsh：被官方点名，只有 14 颗星

生态里最拧巴的项目。官方 rc.1 的 release notes 点名了它并声明非官方，Discussions 秀场也给它开帖，但它只有 14 颗星、0 个 fork、59 个 commit。

它是一个治理型发行版：Skill Forge 和 Plugin Forge 让 agent 提案新技能新插件、人来审批；带 Eval 和 Optimizer；MCP 懒激活；能复用你已有的 Claude、Codex、Gemini 配置。工程姿态也认真：钉住 `dsh@0.1.0-rc.8`，每周用 canary 跑上游 next 分支，主动管理 pre-1.0 的冲刷风险。

它的口号值得单独记下："Overlay, not a fork"。不 fork 源码，一切改造发生在插件层和覆盖层。这和上一节 fork 方向的安静互为印证：整个生态的共识是改造在插件层做，这也是"一切皆插件"架构意图的胜利。注意这句口号里藏的成本核算：pre-1.0 阶段上游每几天动一次，fork 意味着每次都要合并冲突，overlay 意味着只在自己那层跟着调。官方把一切都做成可替换的，替换层才有资格选择跟版节奏，"可替换"在这里兑现成了实实在在的维护成本优势。

名气与体量的倒挂说明两件事。生态还早，官方一句点名比社区一万颗星更有权威性，用户找插件先看官方秀场再看榜单。以及"发行版"这条路本身没被验证：用户更愿意单装插件，而不是换一个别人配好的整装包。发行版不受欢迎的深层原因值得替用户想一想：装发行版等于把自己的插件树交给第三方治理，pre-1.0 阶段等于多了一层跟版中介，官方动、发行版动、你的插件动，三层的任何一层都可能成为你坏掉的原因。单装插件把这条链压到两层。用户不是不懂治理型发行版的好，是在算故障链的长度。这两条合起来给后来者的提示是：做插件有市场，做发行版暂时没有。

## 痛点的另一面

生态的痛点全部来自 pre-1.0 的冲刷，社区讨论里有完整记录。对想入场的插件作者，这一节比任何榜单都值钱。

破坏性变更是明牌。README 全大写写着会有兼容性破坏，0.0.1 到 0.1.x 之间命名重构频繁，Discussions #5120 整帖在问"插件怎么跟上版本"。

版本追踪曾是重灾区，机制值得拆开讲。上游全仓两百多个包锁步发版，但发的是预发布号（rc、alpha），而 npm 的 latest 标签不指向预发布。结果：单独安装某个 `@deepseek-ai/dsh-*` 包，npm 会安静地解析到 latest，也就是一个旧版本。社区实测的漂移样例（#4222）：`@deepseek-ai/dsh-agent` 的 latest 解析到 0.1.0-rc.6，实际最新发布是 0.1.1-rc 系。装错了不报安装错误，版本错配以类型错误的形式延迟爆炸，报错分散在运行期，没有一条可搜索的错误串能把人引到"版本不对"这个根因上。这是所有锁步发版加预发布策略的项目的通病，`dsh` 不是特例，只是它发版太快把病灶放大了。

插件 API 有真实缺口。#802 指出：插件能声明合并自己的会话事件类型，但持久化这些事件可能导致其他进程打不开会话。插件作者面临两难，要么放弃领域事件，要么冒写坏会话的风险。官方后来恢复了可忽略事件标记，给了非关键事件一条安全通道，核心事件仍无官方答案。这个缺口的分量要结合"模型可见即可重建"的运行时不变量来读：会话日志是整个系统重建状态的唯一来源，任何第三方事件写进日志都可能破坏可重放性，官方的谨慎不是官僚，是在保护最贵的那条不变量。代价是插件作者的领域状态没有官方归宿，只能绕道存储接缝或外挂文件。

插件作者实际在怎么活过 pre-1.0？社区里沉淀出的打法已经成型，oh-my-dsh 的做法就是模板：把依赖钉在具体版本号上（不追 latest），每周拿 canary 跑一次上游的 next 分支提前撞破坏性变更，坏在 canary 里比坏在用户手里便宜一个数量级。DSH Doctor 这类自动迁移工具再把撞出来的 API 差异半自动修掉。这套流程本身就是 pre-1.0 生态的新工种：跟版工程师。

稳定性是结构性风险。#1884 综述了 AI 生成插件的风险：插件跑在宿主进程里，和你的会话同生共死，一个未捕获异常波及全进程所有会话。#1814 报告过实际事故：装了一个依赖 `dsh-tools` 的插件，全部工具调用被弄坏。进程模型是根因：`dsh` 没有给插件开独立进程或权限沙箱（官方的安全公告明说本项目未经安全审计，插件是明确的信任边界），你装的每个插件都在你的信任圈里全速跑。这条结构性风险的缓解手段就是上一节的隔离观察和最小插件集二分，工具和纪律要配套。

文档缺口由社区填补：CSDN 文档合辑、runoob 教程站、一本社区编的 DeepSeek Harness Handbook。官方文档其实不缺架构和 API 参考，缺的是中文的入门路径和踩坑实录，这三块补的全是"一个新作者从零到发出第一个插件"的那段路。社区文档的繁荣度历来是生态健康度的先导指标，比插件总数更早反映真实参与。

这些痛点里有一条共性：它们都不是"功能不够"，而是"边界不稳"。发版节奏、API 缺口、进程模型，全是插件作者和宿主之间的接口问题。一个生态的成熟度，看的从来不是插件数量，而是这层接口的稳定程度。

## 痛点长出了新插件

这个生态最健康的信号，是痛点本身催生了诊疗工具链。上一节列的四类痛点，每一类都能在下面对到一味药，药全是患者自己配的。

DSH Doctor 识别版本之间的 API 变化并自动迁移插件，直接对着版本漂移那个坑；dsh-plugin-reducer（#3686）用最小插件集做二分诊断，定位是哪个插件弄坏了宿主，对着 #1814 那类"装了一个、坏了一片"的事故，方法就是经典的对分法，每次砍一半插件重启，log₂ 次定位凶手；topology（#1565）画插件依赖图，对着"装 A 必须先装 B"的隐性依赖；AgentDebugX 是一个学术演示（EMNLP 2026 demo），做 agentic AI 的调试。

调试工具链的出现比插件数量更有含金量。四千个插件说明人多，自建的诊疗工具说明这些人在认真长期地用，而不是发完即弃。打个比方：夜市开满摊位说明有客流，摊主们自费请了维修工说明他们打算长干。对照成熟生态（VS Code、Obsidian）的历史，插件医生、依赖诊断这类工具都是在生态规模上来之后才出现的，`dsh` 生态用一个月走完了信号出现这一步。

## 度量战争会怎么收场

顺着现有机制推一步，以下是我的推断，不是官方表态。

星数榜不会自愈。只要官方通道还是开放标签、只要聚合市场还有按星排序的动力（星数是最容易抓到的全站指标），挂标签蹭流量的行为就持续有收益。dshmarket 的下载口径会越来越成为事实标准，因为它度量的东西（装机）和用户的决策（装哪个）是同一个动作的两面。但下载口径也有自己的天花板：它看不出插件装上之后是被用还是被卸，看不出小众但关键的插件（比如给某个行业 MCP 做的桥）的真实价值，长尾里下载量为个位数的插件可能是某个团队的生产依赖。

真正的变量在官方。三个可能的动作都会改变战场：官方出一个"verified"清单（哪怕只是把 Discussions 秀场结构化），星数榜的导航价值立刻腰斩；npm 发布走 org 命名空间加 provenance，冒名和蹭标签的空间收窄；1.0 稳定 API 落地，插件兼容性从"每几天重验"变成"季度事件"，市场的角色从避雷器退化成目录。哪个先来不确定，确定的是战争收场的形状：度量回归它该度量的东西，装了什么、谁在维护、和哪个版本测过。在那之前，本文的判断清单就是过渡期的自卫手册。

交代一下本文数字的来历，供你复现。星数和标签仓库数取自 GitHub topic 页面（dsh-plugin 话题），装机数据取 dshmarket 的 npm 周下载排序，两个来源 9 月 5 日当天交叉核对过一次。真身查证用的是前面交代的三步法（clone、grep import、读依赖表），抽查对象以榜单头部和本文点名项目为准，不是全量审计，13,760 个挂标签仓库里没有逐一验证过，这个抽样偏差你应当知道。数字会过期，方法不会，这也是复现的价值所在。

## 挑插件的一套判断

把全文收成可执行的清单。回到下午的任务模板化：任何一次装插件，走这五步。

看下载不看星。星数榜已被标签流量污染，npm 周下载是装机量，dshmarket 的口径目前最干净；查的时候注意它的已知瑕疵（缓存和 CI 造成的重复计数），把它当热度读，别当精确用户数读。看作者的插件列表：多产作者的质量信号强于单品的星数，一个人连续维护四个高装机插件，比一个四万星的一次性项目可靠得多。问它声明测试过的 `dsh` 版本：pre-1.0 阶段这是必答题，答不出来的插件默认会坏在下个 release；更进一步，看它是钉住版本还是追 latest，钉版本的作者至少证明自己想过跟版这件事。看市场姿态：锁注册表、默认禁 build script、不收遥测的 dshmarket，比照单全收的聚合器可信，因为前者对"进榜"这件事设有门槛。AI 生成的插件先隔离观察：#1884 的教训是一个未捕获异常、全进程所有会话买单，宿主进程模型决定了插件故障的爆炸半径就是你的一切。

拿第二个任务把清单走活：你要一个消息编辑插件，候选是双雄。第一步查下载和星数：两个都是小几十星的小项目，装机数据都不大，第一条信号失效，这正是清单要按序执行的原因。第二步看作者：DSH-EasyRewrite 被官方秀场转发过，作者和官方有可见的互动记录，这算履历上的硬信号。第三步问版本：两个项目 README 里声明的测试版本，是它们能否活过下个 release 的直接预测。第四步看分发渠道。第五步隔离观察。走到这里你会发现，真正的决策点其实不在清单里，而在需求里：你要的是改错字的顺手（原位编辑），还是要探索另一条回答路径（分支树）。清单负责把"不值得看"的筛掉，剩下的选择回到你自己要什么。这是所有评测工具的边界，也是它们正确的用法。

清单背后的一条总原则：这个生态里，可信度的来源从"官方审核"（不存在）换成了"装机事实加作者履历"。你在用市场信号替代缺席的守门人，所以信号本身的质量决定你的决策质量。

最后一条关于数据本身：本文所有数字是 2026 年 9 月 5 日的快照，这个生态的月增速是数量级的，任何数字用前重查。判断方法比数字耐用，这也是本文把方法放在数字前面的原因。
