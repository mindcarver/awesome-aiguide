# dsh 子代理模型路由：授权-选择-执行三层

> 把任务委派给子代理时，"它用哪个模型"在 `dsh` 里不是运行时可以商量的问题。委派的子会话审批策略被钉死为 never，因为后台子代理发起询问没有任何界面能看到，问了就是隐形阻塞。于是模型路由被拆成三道事前的门：用户在 Host 设置里授权一张精确到 provider 加 model 对的白名单；会话创建时把白名单快照成持久事件，子会话继承、恢复会话用当时的记录；执行器在实际调用前独立复核，中途新装的适配器不得静默扩大这张表。本篇按 2026 年 9 月初的源码和两篇设计笔记拆这三层，外加两条显式拒绝：ACP、Claude Code、Codex 传输不支持动态选择且配了就报错，fork 委派禁用选择是因为换模型会让复制的前缀失去 KV 缓存复用资格。

## 问题：子代理用什么模型，谁说了算

父 agent 把"分析这三十个文件"委派给子代理，马上出现一串问题。子代理默认继承父 agent 的模型吗？部署者想规定"子代理只准用便宜的 flash 模型"，这个意图怎么表达？模型目录里新上线一个模型，子代理能不能自动用上？

回答之前要先看一条更硬的约束。`dsh` 把委派出去的子会话审批策略固定为 never：子代理请求升级权限时，得到的是确定性的拒绝，而不是弹一个问句。这个设计源于一个真实缺陷：后台子代理发起询问后，没有任何界面能展示它，用户看不见、答不了，会话就卡在那里。官方的解法是不许问，子代理的权限边界在委派那一刻就固定下来。

不许问，加上模型选择直接影响成本和授权边界，结论就清楚了：凡是影响成本与边界的决策，都不能依赖运行时的人类应答，必须全部前置。模型路由的三层设计是这个结论的落地。

## 三十秒模型

三层各管一段。授权层：用户事先在 Host 设置里签发一张白名单，每一项是精确的 provider 加 model 对，不是前缀，不是通配符。快照层：每个新会话创建时，把这张表拍成一条持久事件存进会话日志；子会话继承这条记录，恢复旧会话时用当时记录的旧表，改设置只影响之后新建的会话。执行层：委派执行器在实际调用模型之前，自己再对照一次白名单，表上没有的路由直接拒绝。

一句话：授权管"能选什么"，快照管"当时能选的是什么"，执行层管"现在调用的确实在表内"。三层里任何一层单独存在都不够，只有授权没有快照，恢复的会话会按新授权跑，历史不可复现；只有快照没有执行层复核，模型在自由生成的工具参数里塞一个未授权路由，校验就成了摆设。

## 授权层：一张精确到模型对的白名单

设置项叫 subagent-model-selection，内容是一个开关加一个列表，列表每一项是精确的 {provider, model}。没有前缀匹配，没有通配符。

精确是有意的。授权的语义是"这些路由用户逐个看过并同意"。如果允许前缀匹配，任何新上线的模型都会自动落在授权范围内，这和整个设计的钉子"新适配器不得静默扩权"直接冲突。想加模型，改表，让用户之手过一遍。

白名单的生效方式有个关键细节：授权存在 Host 层的设置里，但真正起作用的是会话日志里的快照事件 subagent/model-selection-policy。会话创建时拍快照，这个动作把一条 Host 设置变成了会话事实。恢复三个月前的会话，用的是三个月前的表。这是"模型可见即可重建"纪律在授权面上的延伸：一个会话的授权状态必须能从它自己的日志重建，而不是依赖读取当下的全局配置。

## 选择层：调用参数怎么带上模型

授权给了范围，选择层决定每次委派实际用哪个。委派工具的可选参数里，provider 和 model 必须成对出现，单给一个就拒绝；reasoning_effort 可以单独给，前提是目标路由可解析。

三个来源按优先级合并：provider 自己的静态默认是基线，部署配置可以覆盖它，这一次调用的参数优先级最高。provider 没有静态默认时，回退到父 agent 最近一次已记录请求里的兼容字段，第一次请求前则用创建选项。

一个容易忽略的细节：换了路由但没带显式 effort 时，继承来的 effort 会被清掉，让新模型解析自己的默认值。不同 provider 的 effort 语义并不对齐，把 A 家的 effort 值直接喂给 B 家的模型，是错配的常见来源，清掉比继承安全。

选择层还有一个配套的发现工具 list_subagent_models，给模型看"现在能选什么"。它的可见集是活的模型目录与授权快照的交集：没授权的不显示，防止模型把时间花在会被拒绝的选项上。反过来，授权了但目录没列的仍然可用，目录只是参考，授权才是硬闸。

## 执行层：执行器不信任上游

按说选择层已经校验过参数，执行层为什么还要再查一遍？因为这个链路上游是模型的自由生成。工具参数是模型写出来的，选择层校验通过之后、执行层拿到之前，中间还隔着异步的预检等待。热更新场景下还有一个时间差：异步预检完成后要复查同一个 provider 实例仍然注册着，否则可能出现 A provider 的默认配置跑进 B provider 的进程。

所以执行层在调用模型解析接口之前，独立再校验一次路由白名单。这是防御性设计的标准形状：校验放在离副作用最近的位置，而不是信任上游传来的"已校验"。

这一层也是"新适配器不得静默扩权"的落点。装了新适配器、模型目录里多了新模型，都不会自动进入子代理的可选集。要进，用户改授权表。对一个把子代理设计成无人值守的系统来说，这是唯一站得住的默认值。

## 两条显式拒绝

能力门。每个子代理 provider 声明一个能力标志，表示自己的传输是否支持动态模型选择。进程内派生、fork、DSH SDK 这三类广播支持；ACP、Codex、Claude Code 三类广播不支持，而且是显式拒绝：配置里写了选择参数，挂载直接失败，不是静默忽略。发版说明里"给 Claude Code 和 Codex 子代理配置模型"指的是 provider 实例上的固定 model 字段，原样传给对方产品的会话，不是动态选择。宁可挂载失败也不静默降级，这个取舍贯穿整个子代理面：配了没生效是最难排查的一类问题，显式报错把它消灭在设计里。

fork 为什么禁用选择。fork 委派的机制是复制父会话的前缀开一个新代理，复制的前缀本来能吃到 provider 侧的 KV 缓存复用：相同前缀的请求，provider 不必重算。换了 provider 或 model，这个资格立即失效，整个前缀重算，成本可能超过委派任务本身。设计笔记把这条写成了显式决策：在路由变更能保留缓存复用、或者能显式暴露有界的重算成本之前，不对 fork 开放选择。一个能力被禁用的理由是算得过账的工程判断，不是没做完。

## 常见误解

授权表管的是委派执行，不管父 agent 自己。父 agent 用什么模型由它自己的路由决定，和这张表无关。快照不会随设置热更新，快照在会话创建时定格，改设置只影响新会话，恢复旧会话永远用记录值。"给 Claude Code 子代理配了模型就是动态选择"也不成立，那是固定字段，能力门上写明的是拒绝。

## 权衡与边界

这套设计的所得是确定性和可审计：授权进入会话日志，任何一次委派用的什么模型、凭哪条授权，事后可查。所失是灵活性：换路由要动设置，新模型要过用户之手，快照期内授权冻结。在"子代理不许问人"的前提下，这个交换是合理的；如果未来子代理获得了可见的审批通道，这张表的形态可能会松动。

本文依据 v0.1.3-alpha.1 前后的源码和两篇设计笔记（2026-08-18 的选择语义、2026-08-24 的授权面），pre-1.0 阶段字段名和事件名仍可能调整，三层结构本身比字段名稳定。
